The main improvement upon the naive approach of iteraing each subsequent element after each element, which is O(n^2), is implementing a hashmap where the key is the number in nums and the value is the index. This allows us to figure out in O(1) time if the current number + some number, which can be called the "complement" == target exists in the hashmap. While intuitively done in two passes or O(n), really O(2n), this can be done in one pass where before adding the element to the hashmap, we check if the complement already exists. If it does we can return the two indices, as the constraints guarantee one solution. If it doesn't we add it to the hashmap ensuring that it may be the complement for the next numbers. Because we store the value as the key and we use a hashmap, we have amortized O(1) lookup and assuming a decent hash function, we can leverage O(1) lookup instead of O(n) linear search to find the solution.
